## 十一、根因分析：清洗管线的四处结构问题

以下均由上面的实测数据反推，均**不是数据源的问题**，而是管线设计问题。

### C7 站点 cleaner 与通用清洗互斥（`content_cleaner.py:157-165`）

```python
if cleaner:
    parsed_result = cleaner(parsed_result)      # 只重写正文
else:
    parsed_result = _default_clean(parsed_result)  # 空白规范化 + 全角归一
```
配了站点 cleaner 的 3 个站点（chictr / clinicaltrials / fiercepharma）**完全跳过通用清洗**。实测后果：
- 幂等性失败中 **0 条归因于本缺陷**（0）；另 0 条属 C9，见下
- 这 3 站的正文含连续多空格 / Tab / nbsp，从未被折叠
- 这 3 站的 `structured_data` 也从未做全角归一（C10 在它们身上也没生效）

修复方向：改成 `cleaner → _default_clean` 串联，而不是二选一。

### C8 `extra` 容器绕过清洗（`content_cleaner.py:99-104` vs `storage_writer.py:71`）

`_default_clean()` 只遍历 `parsed_result["structured_data"]`，而落库信封的 `extra` 取自**另一个顶层键** `parsed_result["extra"]`（`storage_writer.py:71`，由 `router.py:90` / `api_router.py:210` 写入）。
- 代码层面可确定：`extra` 从不经过 `normalize_whitespace` / `full_to_half`
- 存量证据只能间接看到：0 处 `extra` 字段值仍含全角标点/多空格，且全部集中在 chictr —— 但 chictr 同时命中 C7，两者叠加，**无法从存量单独隔离 C8 的贡献**
- 风险：只修 C7 而不修 C8，`extra` 仍会脏；C7/C8 必须一起改
- 影响：站点特有字段（chictr 的招募标准、intervention 等）以未归一原文进入信封与下游

修复方向：`_default_clean` 同时遍历 `extra`，或在 storage 层统一归一。

### C9 frontmatter 使用未清洗的 title（`content_cleaner.py:65-90, 171`）

`_inject_metadata()` 在清洗之后执行，但取的是**顶层 `title`**，而 `title` 从未经过 `clean_title()`。
- 幂等性失败中 **0 条归因于本缺陷**（脏字符藏在 frontmatter 的 `title:` 行里，正文本身是干净的）

修复方向：frontmatter 注入前对 title 执行 `clean_title()`。

### C10 `full_to_half` 改写中文标点（**2026-10-27 已修**）

`full_to_half()` 原先转换整个 U+FF01–FF5E 区段，`，：；（）` 会被转成 `,:;()`：「自选课题（自筹）」→「自选课题(自筹)」。
- 实测全库字段值：**全角字母数字 0 个，全角中文标点 408 个** → 整段转换 100% 有害、0 收益
- 已改为 `full_to_half(text, alnum_only=True)`：清洗管线只转全角数字/字母/空格，中文标点原样保留；标识符抽取仍走默认整段转换

> **不属清洗问题的部分**：23 条标题为空、16 条日期为空、站点字段填充率 29% —— 这些是采集端 `css_extract` 未命中，清洗层拿到的就是空值，无法补救。见 §二 / §八。
