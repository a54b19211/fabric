# 消歧引擎方案

## 一、目标

消歧引擎用于判断 LLM 从文档中抽取出的实体是否已经存在于 `entity_dict` 中。

例如：

- “恒瑞”
- “恒瑞医药”
- “江苏恒瑞医药股份有限公司”
- “Jiangsu Hengrui Pharmaceuticals”

这些名称可能指向同一个真实世界实体，系统需要将其绑定到同一个 `entity_dict.id`。

推荐原则：

> 确定性规则优先，向量召回辅助，LLM 只做精排和解释，不直接自动落锤。

当前项目已有基础：

- `flows/extraction_flow.py` 中已有 `_disambiguate()`，但目前只做别名精确匹配。
- `db.repository.lookup_alias()` 已支持 `entity_aliases` 精确查找。
- `db.repository.search_similar_entities()` 已预留 pgvector 相似度检索。
- `db/schema.sql` 已预留 `entity_aliases.name_embedding vector(1536)`。

缺失部分：

- 独立的 `disambiguation/engine.py`。
- 完整的消歧结果结构。
- 名称规范化。
- 多候选返回。
- 向量召回接入。
- LLM 精排策略。
- 审核通过后的 alias 回写机制。

---

## 二、总体流程

```text
抽取实体
  ↓
名称规范化
  ↓
强 ID 匹配
  ↓
别名精确匹配
  ↓
实体类型规则匹配
  ↓
向量召回候选
  ↓
LLM 精排（仅模糊场景）
  ↓
输出消歧结果
  ↓
写入 extracted_entities.dict_id / 进入审核队列
```

---

## 三、输入设计

不要只传 `name_cn / name_en / entity_type`，建议传完整上下文：

```python
def disambiguate(
    entity_name: str,
    entity_type: str,
    entity_data: dict | None = None,
    source_text: str = "",
    source_site: str = "",
) -> DisambiguationResult:
    ...
```

字段说明：

| 字段 | 作用 |
|---|---|
| `entity_name` | LLM 抽取出的原始实体名 |
| `entity_type` | 实体类型，必须参与匹配，禁止跨类型消歧 |
| `entity_data` | LLM 抽出的结构化字段，用于强 ID 和规则匹配 |
| `source_text` | 原文片段，供 LLM 精排和前端解释使用 |
| `source_site` | 来源站点，用于判断可信度和 canonical 合并优先级 |

---

## 四、输出设计

建议定义：

```python
@dataclass
class DisambiguationResult:
    status: str
    dict_id: int | None
    confidence: float
    matched_name: str
    reason: str
    candidates: list[dict]
```

### status 定义

| status | 含义 | 后续动作 |
|---|---|---|
| `auto_matched` | 外部 ID、精确别名或高置信规则命中 | 绑定 `dict_id` |
| `candidate_matched` | 向量或 LLM 认为存在可能候选 | 进入人工审核，展示候选 |
| `new_entity` | 没有找到合理候选 | 作为新实体进入审核 |
| `ambiguous` | 多个候选接近，无法自动判断 | 必须人工确认 |

如果需要兼容早期 `dev_plan.md` 中的三态：

```text
auto_matched / vector_matched / new_entity
```

可以内部保留四态，对外将：

```text
candidate_matched + ambiguous → vector_matched
```

但建议内部保留更细的状态，便于前端展示和后续调优。

## 五、分层策略

## Step 0：名称规范化

在任何匹配前，先生成候选名称集合。

### 通用规范化

- 全角转半角。
- 英文统一小写。
- 中文括号、英文括号统一。
- 多余空格、点号、连字符归一。
- 去除首尾无意义标点。
- 保留原始名称。

### Company 规范化

可去除或弱化以下后缀：

- `有限公司`
- `股份有限公司`
- `有限责任公司`
- `Inc.`
- `Ltd.`
- `Limited`
- `Co., Ltd.`

但原名仍要保留，规范化名只作为辅助匹配。

### Drug 规范化

谨慎处理剂型：

- `片`
- `胶囊`
- `注射液`
- `颗粒`
- `滴丸`

药品名称中剂型有时是正式名称的一部分，不能简单删除后直接自动合并。

建议：

```text
原名精确匹配优先
规范化名只用于候选召回
```

### 候选名称来源

```python
names = [
    entity_name,
    normalized(entity_name),
    entity_data.get("name"),
    entity_data.get("name_en"),
    *entity_data.get("aliases", []),
]
```

---

## Step 1：强 ID 匹配

优先使用外部 ID，不依赖名称。

不同实体类型的强匹配字段：

| 实体类型 | 强 ID 字段 |
|---|---|
| Company | 统一社会信用代码、LEI、股票代码 + 交易所 |
| Drug | DrugBank ID、NMPA 批准文号、CAS、INN |
| Target | UniProt ID、HGNC ID、gene_symbol |
| Indication | ICD、MeSH |
| ClinicalTrial | NCT 编号、CTR 编号 |
| ApprovalEvent | approval_number |
| Compound | CAS |
| Policy | 文号 + 发布日期 |
| Pathway | KEGG ID |

命中规则：

```text
强 ID 完全一致
  → auto_matched
  → confidence = 0.99
```

示例原因：

```text
external_id matched: nct_id=NCT01234567
```

---

## Step 2：别名精确匹配

调用已有接口：

```python
lookup_alias(name, entity_type)
```

匹配顺序：

1. 原始实体名。
2. `entity_data.name`。
3. `entity_data.name_en`。
4. `entity_data.aliases`。
5. 规范化名称。

推荐置信度：

| 命中类型 | status | confidence |
|---|---|---|
| 原始名精确命中 | `auto_matched` | 0.95 |
| alias 精确命中 | `auto_matched` | 0.95 |
| 规范化名命中 | `auto_matched` 或 `candidate_matched` | 0.90 |

其中规范化名命中是否自动通过，要按实体类型决定：

- Company 可偏自动。
- Drug、Target、Compound 建议进入候选审核。

---

## Step 3：实体类型规则匹配

不同实体类型需要少量专门规则。

### Company

高置信规则：

```text
股票代码 + 交易所一致
  → auto_matched
```

弱规则：

```text
中文简称相似 + 英文名相似
  → candidate_matched
```

### Drug

高置信规则：

```text
CAS 一致
批准文号一致
DrugBank ID 一致
  → auto_matched
```

弱规则：

```text
研发代号一致
商品名相似
INN 相似
  → candidate_matched
```

原因：药物研发代号、商品名、授权后名称可能变化，不能只靠名称自动合并。

### Target

高置信规则：

```text
UniProt ID 一致
HGNC ID 一致
  → auto_matched
```

中等置信规则：

```text
gene_symbol 一致 + species 一致
  → candidate_matched 或 auto_matched
```

### ClinicalTrial

```text
NCT / CTR 编号一致
  → auto_matched
```

### Compound

```text
CAS 一致
  → auto_matched
```

### Policy

```text
文号 + 发布日期一致
  → auto_matched
```

只有标题相似时，不自动合并。

---

## Step 4：向量召回

前面都没有高置信命中时，使用向量召回候选。

现有接口：

```python
search_similar_entities(
    embedding: list[float],
    entity_type: str,
    top_k: int = 5,
) -> list[dict]
```

需要新增 embedding 生成函数：

```python
def embed_entity_for_disambiguation(
    entity_name: str,
    entity_type: str,
    entity_data: dict,
) -> list[float]:
    ...
```

推荐 embedding 文本：

```text
实体类型: Drug
名称: 阿司匹林
英文名: Aspirin
别名: ASA, acetylsalicylic acid
关键字段: CAS=50-78-2
```

不要只 embedding 名称，否则容易把语义相近但不是同一实体的对象召回。

### 向量阈值建议

| 条件 | 处理 |
|---|---|
| top1 >= 0.92 且 top1 - top2 >= 0.05 | `candidate_matched` |
| top1 >= 0.85 | `candidate_matched` 或 `ambiguous` |
| top1 < 0.85 | `new_entity` |

原则：

```text
向量只做召回，不直接 auto_matched。
```

原因：医药领域实体名称相似但含义不同的情况很多，例如：

- `PD-1`
- `PD-L1`
- `anti-PD-1 antibody`
- `PD-L1 inhibitor`

它们向量可能接近，但不是同一个实体。

---

## Step 5：LLM 精排

LLM 不作为默认路径，只在模糊场景调用。

触发条件：

1. top1 和 top2 分数接近。
2. 候选名称相似，但实体类型复杂。
3. `entity_data` 信息丰富，规则无法判断。
4. 前端需要辅助审核解释。

输入示例：

```json
{
  "extracted_entity": {
    "entity_type": "Drug",
    "name": "...",
    "entity_data": {},
    "source_text": "..."
  },
  "candidates": [
    {
      "dict_id": 1,
      "canonical_data": {},
      "aliases": []
    }
  ]
}
```

输出要求：

```json
{
  "matched_dict_id": 123,
  "confidence": 0.88,
  "decision": "same_entity | different_entity | unsure",
  "reason": "..."
}
```

LLM 决策规则：

| LLM 输出 | 系统处理 |
|---|---|
| `same_entity` 且 confidence >= 0.9 | `candidate_matched`，进入审核 |
| `unsure` | `ambiguous` |
| `different_entity` | `new_entity` |

不建议 LLM 直接产生 `auto_matched`。

---

## 六、写库策略

### 命中已有实体

写入：

```python
extracted_entities.dict_id = result.dict_id
```

前期建议所有实体仍进入人工审核：

```python
review_status = "pending"
```

稳定后再考虑：

```python
if result.status == "auto_matched" and result.confidence >= 0.97:
    review_status = "auto_approved"
```

### 新实体

建议采用保守方案：

```text
new_entity 不立即写入 entity_dict
只写 extracted_entities，dict_id = None
审核通过后再创建 entity_dict
```

这样可以避免错误实体污染字典。

备选激进方案：

```text
先创建 entity_dict，is_verified=False
审核通过后改为 is_verified=True
```

不推荐在早期使用激进方案。

### 审核通过后的 alias 回写

当审核员确认某个抽取实体属于已有 `dict_id` 后，应自动补充 alias：

- `entity_name`
- `entity_data.name`
- `entity_data.name_en`
- `entity_data.aliases`

写入 `entity_aliases`，提升后续命中率。

## 七、可能出现的问题与解决方案

### 1. 同名不同实体

例子：

- “ABC” 可能是公司简称，也可能是药物研发代号。
- “HER2” 可能是靶点，也可能出现在适应症描述中。

解决方案：

- 所有匹配必须带 `entity_type`。
- 禁止跨实体类型消歧。
- LLM 输出实体类型后，后端仍必须校验。

---

### 2. 中英文别名不全

例子：

- “恒瑞医药”
- “江苏恒瑞医药股份有限公司”
- “Jiangsu Hengrui Pharmaceuticals”
- “Hengrui Pharma”

解决方案：

- `entity_aliases` 维护多语言别名。
- 审核通过后自动补充 alias。
- Company 做后缀归一化。
- 前端允许审核员手动添加别名。

---

### 3. 药物研发代号复用或更名

问题：

- 一个药物可能有多个研发代号、商品名、通用名。
- 药物授权后名称可能变化。
- 不同公司可能使用相似代号。

解决方案：

- Drug 优先使用 CAS、批准文号、DrugBank ID。
- 单靠研发代号只给 `candidate_matched`。
- 需要展示候选原因，不能只展示分数。

---

### 4. 向量相似但不是同一实体

例子：

- `PD-1`
- `PD-L1`
- `PD-L1 inhibitor`
- `anti-PD-1 antibody`

解决方案：

- 向量只做召回，不做最终自动合并。
- top1/top2 分数接近时直接标记 `ambiguous`。
- 对 Target/Drug 增加字段规则约束。

---

### 5. LLM 编造判断理由

问题：

LLM 可能根据常识强行判断两个实体相同。

解决方案：

- Prompt 明确要求：没有证据就输出 `unsure`。
- LLM 只能基于输入字段判断，不能引入外部知识。
- LLM 结果只作为审核建议。
- 保存 `reason` 供前端展示和追溯。

---

### 6. 字典污染

问题：

错误的新实体或错误合并进入 `entity_dict` 后，会影响后续所有匹配。

解决方案：

- `new_entity` 默认不写入 `entity_dict`。
- 审核通过后再创建 canonical 实体。
- `entity_dict.is_verified=False` 的实体不参与高置信自动匹配。
- 提供人工合并、拆分工具。

---

### 7. 名称规范化误伤

问题：

公司后缀可以去，但药品名、政策标题、化合物名不能简单删词。

解决方案：

- 规范化函数按 `entity_type` 分开。
- 原始名优先，规范化名辅助。
- 药物和化合物的规范化命中不要直接自动合并。

---

### 8. 向量维度不一致

问题：

当前 schema 中是：

```sql
name_embedding vector(1536)
```

如果实际 embedding 模型输出不是 1536 维，插入会失败。

解决方案：

- 明确 embedding 模型。
- 写入前校验向量维度。
- 如果换模型，需要迁移 `vector(n)` 维度。
- `db.models.EntityAlias` 当前没有 `name_embedding` 字段，长期建议补齐，或明确所有向量写入统一走 SQL。

---

### 9. 候选审核体验差

问题：

如果只展示“可能匹配”，审核员无法快速判断。

解决方案：

前端应展示：

```text
抽取实体：恒瑞医药
候选实体：江苏恒瑞医药股份有限公司
匹配状态：candidate_matched
置信度：0.91
原因：alias 相似 / 向量相似 / LLM 判断
候选来源：entity_dict.id=123
```

多个候选时展示：

```text
候选 1：江苏恒瑞医药股份有限公司，相似度 0.91
候选 2：上海恒瑞医药科技有限公司，相似度 0.89
状态：ambiguous，需要人工确认
```

## 八、落地优先级

### P0：可用版

目标：先让消歧引擎独立成模块，并替换当前 `_disambiguate()`。

实现内容：

1. 新建 `disambiguation/engine.py`。
2. 定义 `DisambiguationResult`。
3. 实现名称规范化。
4. 调用 `lookup_alias()` 做多名称精确匹配。
5. 接入 `flows/extraction_flow.py`。
6. 将结果写入 `entities[i]["dict_id"]`。
7. 将 `status/confidence/reason/candidates` 写入 `entity_data` 或单独字段预留。

不做：

- 不接 LLM。
- 不接向量。
- 不自动创建 `entity_dict`。

---

### P1：增强版

目标：支持候选召回和审核辅助。

实现内容：

1. 增加 embedding 生成函数。
2. 接入 `search_similar_entities()`。
3. 返回 top_k 候选。
4. 增加阈值策略。
5. 前端展示候选、原因和分数。
6. 审核通过后自动补 alias。

---

### P2：智能版

目标：降低复杂场景的人工判断成本。

实现内容：

1. 只在 `ambiguous` 场景调用 LLM 精排。
2. 保存 LLM 判断理由。
3. 审核通过后进行 canonical 合并。
4. 引入高置信自动审核策略。
5. 增加错误合并回滚和人工拆分能力。

---

## 九、推荐决策规则

```text
外部 ID 一致
  → auto_matched, confidence=0.99

别名精确命中
  → auto_matched, confidence=0.95

规范化名称精确命中
  → auto_matched 或 candidate_matched, confidence=0.90

向量 top1 >= 0.92 且 top1 - top2 >= 0.05
  → candidate_matched, confidence=top1

向量 top1 >= 0.85
  → candidate_matched 或 ambiguous

无候选
  → new_entity

LLM 只用于 ambiguous 场景
  → 给审核建议，不直接自动合并
```

---

## 十、建议结论

建议先实现 **P0 + P1**，暂缓 LLM 精排。

原因：

1. P0 能快速替换当前只有 `lookup_alias()` 的薄实现。
2. P1 能把候选和原因提供给审核前端，形成可用闭环。
3. LLM 精排成本高、不可完全信任，适合等审核数据积累后再接入。
4. 早期最重要的是避免 `entity_dict` 污染，所以新实体和模糊实体都应先进审核队列。
