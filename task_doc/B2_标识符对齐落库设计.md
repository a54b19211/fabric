## 一、为什么必须落库

对齐结果 `parsed_result["authority_resolutions"]` 目前走完全程后**没有归宿**：

| 查哪里 | 有没有对齐结果 | 证据 |
|---|---|---|
| `documents` 表 | ❌ | 无对应列 |
| `doc_extra` 表 | ❌ | 只有 `extra JSONB` 一列，语义是「来源特有字段」 |
| `data/lineage/` | ❌ | 15 站 53 个字段并集里不存在 |
| 落库信封 `json_envelopes/` | ❌（存量 150 条） | 生成于 2026-09-20，早于对齐能力 |
| `core_engine/transform_pipeline.py:74` 注释 | — | 「并把对齐五元组存入 `authority_resolutions`（**落库由 C 组负责**）」——从未实现 |

**后果，用论文语言说**：`accuracy` 维度里「对齐命中 +0.2」这一项，对任何**已入库文档**都无法复算；「标准标识符对齐」作为辅创新，只能展示单篇样例，无法给出全库对齐率。

**后果，用工程语言说**：`resolve_identifier` 每次调用实测 1.4~3.4 秒。这个成本已经花掉了，结果只活在一个 Python dict 里，进程一结束就没了。要复用只能重跑联网请求。

## 二、三个方案对比

| 方案 | 做法 | 改动量 | 能否统计对齐率 | 结论 |
|---|---|---|---|---|
| 1 | `documents` 加一列 `authority_resolutions JSONB` | 小（约 5 处） | ❌ 只能整体看，无法按药名/系统聚合 | 否 |
| **2** | 新建 `doc_authority_resolution` 表，一行 = 一个文档的一个药名对齐结果 | 中（约 80 行） | ✅ | **采用** |
| 3 | 塞进 `doc_extra.extra` | 最小 | ❌ 污染 extra 语义，无法结构化查询 | 否 |

选 2 的唯一理由：**只有它能支撑「全库 N 个药名，对齐成功 M 个，命中率 X%」这个可写进论文的数字**，且能按站点、按标识符体系分组。

## 三、表结构

### 3.1 DDL（V020）

```sql
-- V020: T3 标准标识符对齐结果落库
-- 背景：transform_pipeline.apply_identifier_alignment 产出的 authority_resolutions
-- 此前只存在于内存，documents / doc_extra 均无承载位置，导致对齐率无法统计。
-- 一行 = 一个文档中的一个原始药名对齐到权威库的结果。

CREATE TABLE IF NOT EXISTS doc_authority_resolution (
    id              BIGSERIAL   PRIMARY KEY,
    doc_uuid        TEXT        NOT NULL,
    raw_name        TEXT        NOT NULL,              -- 对齐前的原始名（药名/申请号）
    id_system       TEXT        NOT NULL DEFAULT '',   -- PUBCHEM / LOCAL / NDA / NCT / PMID / DOI
    std_id          TEXT        NOT NULL DEFAULT '',   -- 完整标准标识符，如 PUBCHEM:2244
    source_id       TEXT        NOT NULL DEFAULT '',   -- 库内 ID，如 2244
    resolved_value  TEXT        NOT NULL DEFAULT '',   -- 权威库返回的标准名
    confidence      REAL        NOT NULL DEFAULT 0,
    found           BOOLEAN     NOT NULL DEFAULT FALSE,
    degraded        BOOLEAN     NOT NULL DEFAULT FALSE,-- 接口降级（超时/限流），未命中不等于不存在
    candidates      JSONB       NOT NULL DEFAULT '[]'::jsonb,
    aligned_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (doc_uuid, raw_name)
);

CREATE INDEX IF NOT EXISTS idx_dar_doc        ON doc_authority_resolution (doc_uuid);
CREATE INDEX IF NOT EXISTS idx_dar_raw_name   ON doc_authority_resolution (raw_name);
CREATE INDEX IF NOT EXISTS idx_dar_std        ON doc_authority_resolution (id_system, std_id);
-- 只给命中行建索引，用于算命中率时避免全表扫
CREATE INDEX IF NOT EXISTS idx_dar_found      ON doc_authority_resolution (doc_uuid) WHERE found;
```

### 3.2 字段来源对照

| 表列 | 来自 `authority_resolutions[name]` 的键 | 说明 |
|---|---|---|
| `raw_name` | dict 的 key | 即 `_extract_drug_name()` 的返回值 |
| `std_id` | `std_id` | 形如 `PUBCHEM:2244` |
| `id_system` | **由 `std_id` 前缀解析** | `PUBCHEM:CID` → `PUBCHEM`；纯 `LOCAL:` 前缀同理 |
| `source_id` | `source_id` | 与 `raw_value` / `resolved_value` / `confidence` 共同构成「对齐五元组」 |
| `resolved_value` | `resolved_value` | 未命中时等于原始名（不丢值） |
| `found` | `found` | |
| `degraded` | `degraded` | **必须单独存**：降级导致的未命中不能算作「查无此药」 |
| `candidates` | `candidates` | 候选列表，供人工复核 |

### 3.3 三条统计口径（论文可直接引用）

```sql
-- ① 全库对齐率
SELECT COUNT(*) FILTER (WHERE found AND std_id <> '')::float / NULLIF(COUNT(*), 0)
FROM doc_authority_resolution;

-- ② 按站点对齐率（站点要从 documents 取，故表不带冗余站点列）
SELECT d.source_site,
       COUNT(*) AS total,
       COUNT(*) FILTER (WHERE r.found AND r.std_id <> '') AS matched,
       ROUND((COUNT(*) FILTER (WHERE r.found AND r.std_id <> ''))::numeric
             / NULLIF(COUNT(*), 0), 4) AS match_rate
FROM doc_authority_resolution r
JOIN documents d ON d.uuid = r.doc_uuid
GROUP BY d.source_site ORDER BY total DESC;

-- ③ 未命中 Top N（用于改进药名抽取，不是用于改分数）
SELECT raw_name, COUNT(*) AS miss
FROM doc_authority_resolution
WHERE NOT found AND NOT degraded
GROUP BY raw_name ORDER BY miss DESC LIMIT 20;
```

**口径红线**：②的 `match_rate` 是**采集端能力指标**，不等于数据质量。未命中可能是药名抽取错（缺陷 1）、也可能是 PubChem 本来就没有这个中文名。论文里必须写成「对齐命中率」，不能写成「标识符准确率」。

### 第 4 步为什么要「先删后插」

`upsert_document` 是幂等的（同 uuid 只更新）。若对齐结果用 INSERT ... ON CONFLICT，药名换了（抽取规则变了）会留下孤儿行。先按 `doc_uuid` 全删再插，与「文档重采 = 该文档对齐结果整体替换」的语义一致。

## 五、与 B3 过渡方案的关系

B3 已实现（2026-10-22）：

| B3 产物 | 位置 | 建表后的去向 |
|---|---|---|
| 信封字段 `authority_resolutions` | `biz_rules/schemas.py::MetadataEnvelope` | **保留**，作为原始凭据 |
| 旁路存档 | `core_engine/authority_store.py` → `data/authority/<site>/<uuid>.json` | 第 6 步回填数据源；双写期过后可停写，文件保留 |
| 落库返回值统计 | `write_to_database` 返回 `authority_total / matched / match_rate` | **保留**，供上层汇总 |

也就是说 B3 不是白做：它产出的旁路文件正是第 6 步的输入。
