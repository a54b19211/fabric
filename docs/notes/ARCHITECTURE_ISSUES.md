# 架构缺陷与优化清单

> 更新日期：2026-09-20
> 本文档记录当前架构（`test-suite` 分支）梳理出的核心缺陷、根因分析与优化方向，用于指导后续改进的优先级决策。
> 与 `ARCHITECTURE.md`（架构现状介绍）配合阅读，本文档聚焦「问题与优化」。

---

## 1. 核心问题主线（因果链）

当前架构最大的问题，是「自动化 vs 质量」的权衡点被放在了**抽取/消歧层**，代价全部堆到了**下游审核层**：

```
NER 信息损失（异构数据同构化过猛）
        │
NEL 消歧保守 + 链路失效（向量召回空转、Step6 禁用、仅精确匹配落锤）
        │
大量实体无法自动链接 → 全部落 new_entity / pending
        │
审核环节被压垮（人工 + Agent 辅助，前端步骤繁杂）
```

两头不讨好：抽取层为了「不误判」放弃自动化，审核层又承担了本不该承担的、且自动化最弱的工作量。

---

## 2. 最具问题的部分（按严重度排序）

### 2.1 消歧链路「实质失效」—— 比设计保守更严重的是实现坏掉了

**现状**：
- Step 4 向量召回当前**空转**：数据库侧已修复（V015 建 `name_embedding` 列 + 装 pgvector 扩展），但 `.env` 未配置有效 embedding key，`generate_embedding` 一直 401 失败。
- Step 6 LLM 兜底被**注释禁用**（`disambiguation/engine.py:146-162`）。

**根因**：NEL 实际只有 Step 1（强 ID）、Step 2（别名精确）、Step 3（类型规则）三条「硬匹配」在工作，**模糊匹配兜底（向量召回 + Reranker + LLM）从未真正提供过候选**。

**影响**：所有没被规则命中的实体只能落 `new_entity` → 进人工审核。这不是「主动保守」，而是「半条腿是瘸的」。

**优化方向**：配置 embedding key 打通 Step 4；Step 6 降级为分级路由的「中置信度复核」——≥0.9 由 Reranker 分数自动落锤、0.7–0.9 调 LLM 复核、<0.7 交人工（**而非恢复全量兜底**，控制延迟）。

**实证案例（2026-09-08 发现）**：`entity_dict` 中 id=199/201/203 三个条目，中文名不同但 `name_en` 完全相同（均为 `Pacsta Co., Ltd.`），本应合并为同一家公司却各自独立成 dict。

- 根因：① 消歧在写库**之前**且**并行**执行，同一批文档里的实体在消歧阶段「互相看不见」（都还没入库），`name_en` 相同也无法互相匹配；② 写库阶段 `batch_dict_cache` 只按 `(entity_type, entity_name)` 中文名去重，不按 `name_en` 去重。
- 印证：若 Step4 向量召回生效，本应通过 `name_en` 的语义相似召回并合并；Step4 空转直接导致这类「同英文名、异中文名」实体漏合并。

### 2.2 交叉验证「连坐」风险（正确性缺陷）

**现状**：`insert_extraction_result` 里（`repository.py:2277-2278`），实体只要第二次命中同一 `dict_id`，原 `pending` 实体就自动置 `auto_approved`，**无置信度门槛**。

**根因**：Step 2 别名精确匹配一旦**误命中**（两个不同实体判成同一 `dict_id`），会触发两条错误链：
1. `auto_approved` 自动放行（跳过人工审核）
2. `_dedup_extracted_entities_by_dict_id` 按 `dict_id` 去重合并，把不同实体的数据并到一起

**影响**：错误不仅「被放行」，还会「被合并传播」，是当前最直接的数据正确性隐患。

**优化方向**：加置信度门槛（仅高置信度才 `auto_approved`），或改为「标记待抽检」而非直接通过。

### 2.3 测试几乎为空（最根本的工程债）

**现状**：`tests/` 仅有 `conftest.py` 的 mock fixtures，**无任何 `test_*.py` 用例**。

**根因**：系统数据完整性靠「软删除 + 无外键 + repository 事务逻辑」保证，**数据库不会帮你挡错误**——代码写错时错误数据会「悄悄」写入，无任何回归测试拦截。

**影响**：每改一行核心逻辑（合并/消歧/审核）都是「裸奔」，功能越多越不敢改。

**优化方向**：从 `disambiguation/` 纯逻辑（normalizer/rules）起步补测试，逐步覆盖 repository → API → Agent。

### 2.4 NER 信息损失（同构化的代价）

**现状**：异构来源统一抽取为 16 实体 + 25 关系的统一 schema。

**根因**：白名单之外的字段被**永久丢弃**；ClinicalTrials API、DrugBank XML 这类**结构化来源被 LLM 重新抽取是「降级」**（本可直接字段映射，却引入不必要误差）。

**影响**：字段级溯源困难，数据质量依赖 LLM 抽取稳定性。

**优化方向**：结构化来源走字段映射直连；关键字段加来源优先级与人工裁决兜底（`_SOURCE_PRIORITY` 已部分实现）。

## 3. 值得优化的地方（按 ROI 排序）

| 优先级 | 优化项 | 收益 | 成本 |
|---|---|---|---|
| 高 | 打通向量召回 + Step6 降级为中置信度复核（配 embedding key、加自动落锤阈值） | 直接减少人工审核量 | 低（代码已就绪） |
| 高 | 交叉验证加置信度门槛/抽检 | 堵住连坐风险 | 极低 |
| 中 | 结构化来源走字段映射（ClinicalTrials/DrugBank 直连） | 消除「降级」，提升数据质量 | 中（需新增适配器） |
| 中 | 补测试（从 `disambiguation/` 纯逻辑起步） | 建立安全网，让后续优化可放心做 | 中（长期收益高） |
| 条件 | redis 队列 + RQ worker、CORS 收紧 | 生产可用性 | 低（决定上线时触发） |

---

## 4. 建议的动作顺序

```
① 补消歧纯逻辑测试（安全网）
   ↓
② 交叉验证加阈值（堵住最直接的正确性 bug，改动最小）
   ↓
③ 打通向量召回 + 恢复 Step6（解锁 NEL 模糊匹配能力，降低审核压力）
   ↓
④ 配 embedding key 后跑一次基线，量化「自动链接率 / 审核工作量」改善
   ↓
⑤ 再决定是否上「结构化来源直连」这种较大改造
```

## 6. 前端文案/展示勘误（与实现不符，2026-09-20 新增）

前端页面按「功能/Agent 类型」组织，而非按「数据流转阶段」组织，导致多处文案/展示与真实逻辑不符、误导用户。梳理如下：

| # | 位置 | 前端展示 | 实际逻辑 | 修改建议 | 优先级 |
|---|---|---|---|---|---|
| 1 | 自动审核页统计卡片 | 「总运行/通过/拒绝/转人工」无单位 | 统计 `agent_run` 条数 = **实体/关系数**，非文档数 | 标注单位「实体 N / 关系 M / 文档 K」 | 高 |
| 2 | 自动审核页 / 文档审核页 | 展示「转人工 escalated」统计/状态 | 实体审核（Agent A）只产出 approved/rejected，**从不 escalated** | 实体审核页去掉 escalated；escalated 只保留在消歧(Agent D)/裁决(Agent B/C)页 | 高 |
| 3 | 自动审核结果 | 「通过」 | Agent A 通过 = `force_new=True`（强制新建 entity_dict，**不链接已有字典**） | 标注「通过（新建实体）」 | 高 |
| 4 | 文档审核页 | 「待审文档」 | 实际筛选「有 pending 实体的文档」（`total_entity_count>0`），非 `done` 文档 | 改名「含待审实体的文档」或加副标语 | 中 |
| 5 | 审核工作台 | 人工「通过」与 Agent「通过」同词 | 人工可 force_new 或选 dict_id 链接；Agent 固定 force_new | 区分「通过（新建）」vs「通过（链接到 XXX）」 | 中 |
| 6 | 数据面板「消歧链接」卡 | 排在「审核」后、无说明 | `dict_id` 是「初步 6step + 精细 AgentD」两段累积结果 | 加副标语说明两段累积 | 中 |
| 7 | 消歧相关页面 | 「消歧」一词未区分 | 初步消歧（6step，抽取时）+ 精细消歧（AgentD，审核后）两段 | 标注「初步/精细」两段 | 低 |

**根源**：同一个字段（`review_status`、`dict_id`）在多个页面以不同维度、不同术语出现；术语（「通过」「转人工」「待审」「消歧」）又与实现有偏差。核心矛盾是「审核」和「消歧」在前端是分离页面，但在人工审核工作台里又是耦合的同一动作（审核员通过时能顺手选 dict_id），而 Agent 自动审核又回到分离（force_new 不链接），三处不一致。

**收敛方向**：① 统一「通过」语义（新建 vs 链接）；② 去掉/标注「转人工」；③ 统计卡片标单位；④ 数据面板/消歧页标「两段」；⑤ 「待审文档」改名。
